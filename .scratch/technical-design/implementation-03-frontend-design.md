## 双方已协商的技术选择

1. 最新预览与下载操作的描述已提及 410，但响应表缺少声明。建议补共享 410：资源本身不存在返回 404；元数据明确记录 `originalAvailable=false` 时返回 410 与 `CONTENT_UNAVAILABLE`；元数据仍标可用而实际读取发生意外故障返回 500 与 `INTERNAL_ERROR`。不通过补项授权清理当前版本，不用最新文件冒充历史正文。历史版本操作已有 410，语义保持一致。前端对 410 显示副本不可用，允许返回元数据；不无条件重试或改用其他版本。
2. 工程起始限额为单份 10 MiB、整个 multipart 请求 100 MiB（含边界等编码开销）、最多 1000 项。换算字节分别为 `10485760`、`104857600`，属于可测工程初值，不能宣称生产性能验收。未来运行配置回显与修改复用同一权威值，前端不另立固定规则。
3. 先完整接收与校验整请求结构及总量，失败返回整体 400 或 413，不产生任何文件提交副作用。总量超限 413 使用 `RESOURCE_LIMIT`。合法数组内的同批重名不是整体结构失败，仍按原契约 200 逐项处理：每个重名组全组 `failed`，其他不重名项继续。单份超过 10 MiB 属逐项失败：整体 200，项目为 `failed`，内含 `RESOURCE_LIMIT` 错误；其他合法项目仍可提交。容器的单份限制不得先于业务层将该情形转成整批 413，其限制至少容纳整个请求限额。文件数与未知 multipart 字段必须按契约拒绝，不因单文件界面省略服务端验证。
4. 纯文本严格按 UTF-8 解码，允许 UTF-8 BOM，原副本和下载保留所有原始字节；预览可移除展示层 BOM。零字节文本合法，不虚构最小字节数。非法 UTF-8 或含 NUL 的二进制内容按不支持文件处理；逐项 200 的错误对象使用 `UNSUPPORTED_FILE`，原始错误状态语义为 415。请求整体不支持的媒体类型与逐项内容不支持必须分开。
5. 文件名按契约完整名称验证，不套用数据集名称的首尾去空白规则；拒绝目录分隔符、控制字符、点或双点及超长名称。上传人由后端运行账号确定，前端不可提交或冒充；`createdBy` 或 `uploadedBy` 为 null 时显示“未知用户”。

上述限额和编码、整体与逐项失败边界须在唯一契约中明确说明，由双方确认新摘要，且回归已有六操作。原契约上传结果没有逐项 HTTP 状态字段，前端不新造 `status` 字段，只消费统一错误对象的 `code`、`message`、`fieldErrors` 和 `retryable`。

## 03 页面与消费方案

沿用数据集页面，在选中数据集的详情区增加资料列表、单份纯文本上传入口和文件详情。列表分页使用稳定标识与不透明游标；详情显示集中名称、数据集、首次创建和最近内容上传时间、上传人，以及最新内容版本的大小、媒体、版本标识、哈希与副本状态。说明上传完成仅代表资料保存，不代表知识库已索引或已可检索；不生成虚假的索引进度。

上传通过共享会话 Axios 客户端和内存 CSRF 头发送 `FormData`，字段严格为 `files`，单份界面仍编码成该正式数组字段，不自行设置 multipart 边界。检查逐项索引和原提交位置对应，200 不等于全部成功；只在 `created` 等成功项目得到合法文件对象后刷新列表和详情。失败保留已有列表、原文件与用户可理解的错误，网络结果未知时提示重新读取确认，不自动重复提交。

预览通过 Axios 请求完整二进制响应，校验媒体及安全头后严格解码并以纯文本插值或 `pre` 呈现。资料中的 HTML、脚本和事件属性始终作为文本，不使用 `v-html`。切换资料或关闭预览后，旧响应不得覆盖新对象；关闭后焦点回触发按钮。空文本展示明确空态。下载使用共享会话请求二进制并建立短时对象地址，使用安全文件名，完成后释放地址；不把副本路径当公开 URL，不将资料存入浏览器持久化。

文件媒体、`Content-Disposition`、`X-Content-Type-Options: nosniff`、`Cache-Control: no-store` 与预览内容安全策略均按更新后契约验收；只要求完整 200，不假定范围请求或 206。错误为 JSON 时仍须解析统一错误，不把 JSON 错误内容保存成用户文件。

## 跨票范围与验收门槛

03 的用户界面仅为单份纯文本；04 扩展 Markdown 与文字 PDF 的安全渲染，05 扩展批量选择、同批重名组处理、覆盖、重命名和版本查看。03 不提前引入 PDF.js、markdown-it、DOMPurify 或批量冲突界面。

但 `uploadFiles` 正式契约本身已经包含 1 至 1000 项、三种媒体、四种结果、同名哈希与大小判断、稳定文件身份、版本生成及逐项独立提交等规则；它们仍保留在完整分母。03 不能删除规则、把单份测试冒充批量测试，或把确定未实现的后续能力写成“条件未触发”来获得百分之百。

协调最终采用完整公共接口路径：03 提前实现五操作公共后端完整语义，包括三媒体、批量逐项、同名组拒绝、哈希判断及原子覆盖；03 界面仍单份纯文本，04、05 保留专属媒体渲染、批量交互、重命名及版本查看。前端公共客户端须严格消费全部 `UploadResult` 结果、三媒体元数据和二进制，用实际 Axios 请求证明多 `files` 构造，不能将单份界面当作接口限制。固定 PDF、Markdown 资料可用于上传下载字节验证，本票不提前引入两种安全渲染器。

报告区分“当前适用路径通过”与“完整操作完成”：若实施后仍存在正式后续约束未实现，`uploadFiles` 在全项目中继续列未完成，不提前报告完整操作百分之百；只有证据覆盖全部必需约束才升级。03 必须消费测试覆盖三媒体的原字节响应、`created`/`replaced`/`unchanged`/`failed` 四种结果、部分失败、批内重名组失败及稳定文件标识，不能把共同规则后移成条件保留。最终按真实证据记录已实现范围，禁止用适用映射隐藏已知缺项。03 必须证明失败上传不损坏已存在资料；不能为拆票而覆盖或丢失原文件。

当前没有需要用户裁定的新业务含义，待契约单写补项及双方摘要签认后派发实现。资源初值属于待实测技术方案，后端须给出验证依据，未实测前不视为获批产品限额或正式性能结论。

## 测试实施顺序

每轮仅编写一个公共边界的失败测试，观察失败后实现最小行为，再执行相关回归，不先批量写完假想测试。测试不调用私有方法，不模拟自有内部模块，不从实现重算期望；网络外边界允许固定适配器，真实提供方与最终浏览器不得被替身替代。

1. 单份上传的实际 Axios multipart 请求与组件结果：字段、安全头、0 字节及中文文本、合法集中元数据、索引状态不伪造。
2. 文件列表与详情消费：分页、稳定标识、可空上传人、版本/时间/大小/哈希边界、加载失败与重试、旧响应隔离。
3. 纯文本安全预览及原字节下载：UTF-8、BOM、空正文、危险 HTML 文本、错误 JSON、不支持媒体、不可用副本、过期会话。
4. 真实发行包浏览器：创建数据集、上传固定文本、打开详情与预览、实际下载字节核对、非法文件拒绝后原资料重新读取、页面刷新；1280、1440、1920 宽度及长文件名截图。
5. 根据协调批准的跨票范围补服务端整请求限额、逐项独立提交和覆盖失败证据；客户端测试同时覆盖三媒体、四结果、部分失败和批内冲突的真实请求/响应；全契约原始项与未完成项同时报告，双方独立审阅同一不可变报告后交协调验收。

最终执行格式、ESLint、Stylelint、Vitest、组件、构建、浏览器及根统一验证；前端行和分支覆盖率各至少百分之八十，不以代码覆盖率替代契约行为证据。真实模型和外部发布不在授权范围。

# 技术架构草案

## 状态与范围

本文件为待确认的架构建议，已确认约束见 `spec.md`，领域术语见根目录 `GLOSSARY.md`。本阶段不设计具体产品交互，不创建应用工程骨架。

## 领域边界

- 数据接入：数据集管理负责原文件生命周期，知识库管理负责关联文件并触发索引处理。
- 知识服务：知识检索从一个或多个知识库获取结果；知识问答在检索结果基础上生成有依据的回答。
- 其他：具体功能后续确定；不将所有技术基础设施堆入同名通用模块。

## 已确认的部署结构

根 Maven 工程聚合 `server/` 与 `front/`。前端独立开发和构建；后端采用一个 Spring Boot 进程，业务模块严格分包管理，不拆微服务。模块内保留接口、业务逻辑和数据访问的清晰职责。采用 ArchUnit 检查业务模块循环依赖与跨模块直接访问数据访问层，检查纳入持续集成；具体包布局和允许的依赖方向尚待确定。

前端依赖由 pnpm 管理，镜像设为 `https://registry.npmmirror.com/`；提交锁文件，持续集成使用冻结锁文件安装。Maven 负责聚合并调用前端构建，具体插件与运行版本尚待确定。

SQLite 数据访问采用 Spring JDBC 的 `JdbcClient` 和显式 SQL，事务由 Spring 管理。迁移工具需要核实 SQLite 与目标框架版本的兼容性后确定。

模型与 Qdrant 是外部服务，配置本地或远程地址；SQLite 与原始文件位于用户设置的数据目录。Qdrant 的原生存储目录由独立部署的 Qdrant 管理，应用不能将远程 Qdrant 的数据视作本地数据目录中的文件。

## 建议的处理路径

1. 文件上传：前端调用后端，后端保存原格式副本与资料元数据；不调用嵌入模型。
2. 知识库关联：保存关联及处理状态，后台执行解析、切分、嵌入与 Qdrant 写入。
3. 知识检索：验证目标知识库范围，生成查询向量，过滤并检索对应索引，返回可追溯的资料位置。
4. 知识问答：复用知识检索结果，组织上下文并生成回答；由后端校验引用能否映射至有效的原文位置。

后台执行已确认采用 SQLite 持久化任务与应用内执行，不引入外部消息队列。SQLite 事务与 Qdrant 写入无法作为一个本地事务提交，需要设计任务状态、幂等写入和故障重试。多知识库检索需要保证嵌入空间兼容，或分别检索后融合；不能直接比较不同模型的相似度分数。

## 已确认的首批模型服务

生成与嵌入均使用 DashScope，取消本地嵌入模型部署。生成模型 `qwen3.8-max` 的准确接口标识尚待核实；嵌入模型标识与维度尚待确定。初始凭据引用 `AI_DASHSCOPE_API_KEY`，文档和代码不得保存密钥实际值。

生成与嵌入采用独立配置，后续允许用户配置模型地址、标识和密钥。优先使用 OpenAI 兼容接口与 Spring AI 对应适配器，只有兼容接口无法提供所需能力时才评估原生适配器。区域端点与配置的安全存储方式待确认。密钥更换与接口地址调整不能直接作为索引可复用的依据；嵌入模型或处理规则改变时需检查索引兼容性。

## 已确认的质量门禁

- Java：Spotless 使用 Palantir Java Format，SpotBugs 检查缺陷，JUnit 5 验证行为，ArchUnit 验证业务包边界。
- 前端：ESLint 与 Vue 规则、Prettier、Stylelint；Vitest 与 Vue Test Utils 验证行为。
- 前后端各自要求行覆盖率与分支覆盖率均不低于 80%；生成代码与纯配置的排除范围需明确配置。
- 根目录 `mvn verify` 统一运行前后端检查、测试和生产构建；任一必需步骤失败则流水线失败。
- GitHub Actions 执行持续集成。普通流水线使用固定测试资料与模拟模型响应，不依赖真实模型密钥或收费接口。
- 格式化检查只检查差异，不在持续集成中自动修改源码。具体工具版本、格式规则和覆盖率采集方式仍需验证并配置。

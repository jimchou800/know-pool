# 前端需求、界面与交互规格契约

## 问题陈述

用户需要在本机统一管理外部资料，将其组织为可检索的知识库，并通过独立的问答与检索实例使用知识。当前已有被采纳的界面原型，但原型仅演示首页和问答，尚未连接正式后端；完整业务、异常状态、版本语义、接口消费、安全与发行要求分散在多份文档中，不能直接把演示行为当作正式产品。

后续产品会封装为桌面程序。前端需要保持当前网页交付可用，并为桌面宿主保留清晰边界，避免固定端口、浏览器窗口和本地文件路径假设导致封装时重写业务界面。

## 解决方案

以用户已采纳的“紧凑高效”方案为统一视觉基础，建立首页、数据集、知识库、知识问答、知识检索与设置的完整前端需求。业务状态以后端事实为准，接口严格消费双方确认的唯一契约，按现有端到端切片逐步落实。

本文是前端需求、界面、交互、状态、安全、桌面适配与验收的统一规格契约，合并原前端需求与界面探索的已确认内容。本文整理前端职责和验收条件，不创建第二套后端业务规则、第二份接口定义或独立于既有切片的实现排期。`ready-for-agent` 表示需求已整理为实施输入；涉及正式接口的工作仍必须先完成契约定义、双向确认及前置任务验收。

13. 作为资料管理者，我希望逐项看到新增成功、覆盖成功、内容未变或上传失败，以便在部分成功时只重试失败项。
14. 作为资料管理者，我希望同一数据集内同名且内容未变时跳过处理，以便避免重复上传和索引。
15. 作为资料管理者，我希望同名内容变化时保留资料身份并生成新内容版本，以便关联和历史引用保持可追溯。
16. 作为资料管理者，我希望不同名称但内容相同的资料分别管理，以便保留各自归属和生命周期。

18. 作为资料管理者，我希望看到资料名称、大小、类型、上传时间、上传人及所属数据集等必要信息，以便辨认资料。

### 知识库、关联与索引

27. 作为知识库管理者，我希望创建并保存空知识库，以便先配置再选择资料。

29. 作为知识库管理者，我希望关联整个数据集或单份资料并查看关联来源，以便控制知识范围。
30. 作为知识库管理者，我希望关联数据集后新增或更新资料自动进入该库处理，以便范围随资料同步。
31. 作为知识库管理者，我希望撤销一种来源后仍保留其他有效来源，以便不会误下线仍需使用的资料。
32. 作为知识库管理者，我希望对单份资料设置排除，以便阻止它进入指定库而不删除源资料或影响其他库。
33. 作为知识库管理者，我希望被排除资料即使显式加入也保持排除提示，以便理解排除优先于所有关联。
34. 作为知识库管理者，我希望取消排除后仅按仍有效来源恢复处理，以便不会凭空恢复已撤销关联。
35. 作为知识库管理者，我希望看到各文件解析、切片、嵌入、写入阶段及失败原因，以便定位问题。
36. 作为知识库管理者，我希望单独重试失败文件或重试全部失败项，以便恢复处理且不重复成功项。
37. 作为知识库管理者，我希望重试结果区分已入队、已有任务和不再符合条件，以便理解实际执行范围。
38. 作为知识库管理者，我希望看到重试可能再次调用模型并产生费用，以便做出明确选择。
39. 作为知识库管理者，我希望预检切片数量、长度分布、降级拆分、空文本及样例，以便在处理前检查内容完整性和来源。
40. 作为知识库管理者，我希望系统区分自动降级拆分和真正的解析失败，以便不会误把长内容处理当作故障。
41. 作为知识库管理者，我希望新版本处理中或更新失败时明确显示仍使用旧生效版本，以便知道检索所用内容。
42. 作为知识库管理者，我希望查看版本切换关系与处理结果，以便追溯何时由哪份内容生效。
43. 作为知识库管理者，我希望至少一份有效资料完成索引后才能发布，以便不会开放无可检索内容的知识库。
44. 作为知识库管理者，我希望发布条件不满足时保留原发布状态并说明原因，以便修复后重新操作。
45. 作为知识库管理者，我希望主动下线和重新发布知识库，以便控制是否接受知识服务的新请求。
46. 作为知识库管理者，我希望最后一份有效可检索资料移除后显示自动下线原因，以便理解为何不可再被选择。
47. 作为知识库管理者，我希望恢复资料后由我显式重新发布，以便系统不会擅自恢复对外引用。
48. 作为知识库管理者，我希望运行不可用、发布状态和索引任务状态分别显示，以便区分服务故障、下线和更新失败。

51. 作为知识库管理者，我希望修改配置重建时旧索引继续服务、成功后自动切换，以便更新不要求重复发布。
52. 作为知识库管理者，我希望主动下线后重建完成仍保持下线，以便后台任务不改变我的发布决定。
53. 作为知识库管理者，我希望显式重新检查故障依赖，以便恢复可用状态而非无限后台轮询。

### 问答实例与原文依据

55. 作为知识使用者，我希望在知识问答中看到实例名称列表和一个当前窗口，以便像聊天应用一样切换工作。
56. 作为知识使用者，我希望新建“新问答”并在首次提交后才保存，以便空白窗口不长期堆积。
57. 作为知识使用者，我希望一个问答实例对应一个会话，以便历史、输入和知识库范围不会互相串用。

59. 作为知识使用者，我希望手动名称不被首次或后续提问覆盖且允许重名，以便按自己的方式组织会话。

63. 作为知识使用者，我希望同会话在任务结束、失败或取消后再提交下一问，以便避免并行回答相互覆盖。
64. 作为知识使用者，我希望提交后看到检索、生成、校验等阶段，以便知道任务仍在执行。
65. 作为知识使用者，我希望校验完成前不显示回答草稿，以便不把未通过的内容当作答案。
66. 作为知识使用者，我希望切换实例后原任务继续并在列表显示状态，以便处理其他工作后再返回。
67. 作为知识使用者，我希望主动取消任务且迟到结果不覆盖取消状态，以便控制等待与后续提问。
68. 作为知识使用者，我希望断线后查询同一任务状态而非重新提交，以便避免重复调用和费用。
69. 作为知识使用者，我希望应用重启后未完成问答显示中断，以便不会把丢失进度误认为已完成或自动重跑。
70. 作为知识使用者，我希望无依据、部分缺口、矛盾资料、校验失败和服务故障分别说明，以便理解答案的限制。
71. 作为知识使用者，我希望部分知识库不可用时知道遗漏范围，全部不可用时明确终止，以便不误以为已检索全部资料。
72. 作为知识使用者，我希望长会话提示只使用近期完整历史，以便理解上下文限制并补充不清楚的指代。
73. 作为知识使用者，我希望历史回答只辅助理解、本轮仍重新检索，以便不会把历史内容冒充当前证据。
74. 作为知识使用者，我希望点击引用在右侧抽屉查看原文、引用时文件名、内容版本和位置，以便边看回答边核对。
75. 作为知识使用者，我希望旧原文件清理后仍能查看引用快照，以便资料更新不会破坏历史证据。
76. 作为知识使用者，我希望快照不可下载为完整旧文件，以便界面不会承诺不存在的原文恢复能力。
77. 作为知识使用者，我希望问答历史自动保存且删除前确认，以便理解将清理会话与专属引用快照。
78. 作为知识使用者，我希望删除实例取消其任务且迟到响应不复活记录，以便删除可靠生效。

79. 作为知识使用者，我希望独立检索具有自己的入口、名称列表和新建按钮，以便不与生成回答混淆。

83. 作为知识使用者，我希望结果提示资料更新或更新失败及旧版本使用情况，以便理解结果时效。

90. 作为知识使用者，我希望删除检索实例前确认，以便了解会清理实例条件与临时结果而不删除资料。

## 实施决策

### 依据与职责

- 使用领域术语区分资料、文件副本、内容版本、切换记录、数据集、知识库、知识服务实例及知识服务窗口。窗口仅呈现当前实例，不建立重复身份或重复会话。
- 业务以技术规格最新确认项为准，界面以 Q20 已采纳方案为准，接口线上的定义以双方确认的唯一契约为准，执行按代理协作及工程门禁。明确被替代的历史描述不恢复为要求。发现未裁定冲突记录后核实，不自行拼接。
- 检索持久化采用技术 Q49，替代界面早期 Q8；实例删除采用技术 Q50，取消任务并保护迟到结果；名称采用技术 Q48，允许重名并尊重手动名称。
- 前端负责展示、路由、交互、状态、请求构造和响应消费。后端负责权威校验、持久化、任务协调、版本发布与数据清理；禁用按钮不能替代服务端约束。
- 完整接口设计及当前版本以唯一契约为准，双方签认与静态验证见 `docs/agents/api/reviews/baseline.md`，24 票的界面需求与操作映射见 `docs/agents/api/frontend-requirements.md`。本文只描述业务操作族，不另定义 URL、字段、事件名、枚举编码或线上的默认值。

### 已采纳的视觉基线

### 资料与知识库行为

- 数据集、知识库名称去首尾空白、同类不区分大小写唯一，不能为空；不同类型可同名。资料文件名按所属数据集内完整名称含扩展名、不区分大小写匹配，不擅自套用其他对象的名称清洗规则。
- 批量上传独立提交结果，冲突组先由用户选定；失败不回滚其他成功项。覆盖失败不改变原文件和原任务，新版本成功提交后才取消旧版本处理。不同名称同内容不合并。
- 前端可以预检类型、重名和大小以便及时提示，最终结果服从服务端验证。单文件、批次、解析和文本量上限由契约与实测确定，不硬编码未经确认的数值。
- 原格式预览使用 PDF.js、markdown-it 与 DOMPurify 等已选方案，文本与回答按不可信输入处理。解析后的文本不替代原始下载文件，不执行资料中的脚本或指令。
- 文件元数据集中展示，通过稳定标识关联；上传人取后端运行账号快照，获取失败展示“未知用户”，不允许客户端冒充账号。首次上传、内容上传和重命名的时间及版本语义保持区分。
- 数据集关联与单文件关联独立保留，来源并集受单文件排除优先规则约束。显式加入不取消排除；取消排除仅根据有效来源重新纳入。
- 配置编辑覆盖已确认的结构优先、固定长度、PDF 按页策略，硬上限默认 2,000 Unicode 码点、目标重叠默认 200 且按库可调；系统码点计量与模型词元限制分开展示，不把初值描述为最佳效果。
- 展示切片预检、原文位置与处理版本，降级拆分不冒充完整独立表格或代码；资源超限和完整性错误不能以静默截断成功呈现。
- 上传结果、按库文件处理状态、知识库发布状态、运行可用状态是不同维度。只有未排除、有效关联、已索引的资料满足发布条件；服务故障不等同于自动下线。
- 旧生效索引更新期间继续服务，新内容通常按库与文件独立切换；处理配置变更按整库构建验证后切换。更新失败提示仍用旧版本，不能把构建进度当作新版本已经生效。
- 失败重试只选择当前仍有效的失败项，成功项不重复；已有对应任务不重复创建，旧取消任务不复活。后台最多三次尝试含首次不套用于问答自动重试。
- 发布状态为未发布、已发布、已下线。至少一份有效资料完成索引才可发布；最后有效资料移除自动下线，恢复资料不自动发布；重建不改变当前发布决定。
- 普通知识服务仅选择已发布库；管理单库测试为明确例外，通过专门操作验证当前生效索引，不向普通请求加入可绕过发布校验的开关。
- 删除影响与确认区分数据集级联资料、知识库保留原资料、单文件排除仅影响指定库，以及会话或实例专属记录清理；异步清理失败可见且可恢复，不将逻辑删除对象恢复为可用。

### 知识服务状态与证据

- 空白问答暂名“新问答”，首次提交后持久保存，不等待回答成功；未提交的空白实例重启不保留。自动标题截取长度尚待对应切片确定。自动标题截取首问且不调用模型；后续输入不覆盖标题。产品会话由后端保存，原型浏览器存储仅为演示，不能直接成为正式持久化方案。
- 切换实例保留运行期输入、知识库范围和结果，任务继续。保存未提交草稿以跨重启恢复尚未确认，不作为默认承诺。
- 单会话最多一个未结束任务，跨实例遵守共享并发和有界队列。前端处理重复点击及繁忙反馈，后端原子约束仍是事实来源。
- 普通请求使用 Axios，SSE 仅推送阶段与完成通知；提交取得任务标识，断线后查询原任务，不自动重新提交或重跑模型。终态结果以持久化查询为准，不能只保存在事件流。
- 未校验回答不得流式展示。生成、校验失败或无有效依据时不呈现草稿；失败、取消、中断仅展示规定状态与脱敏原因。问答不自动重试，用户可显式重新发起。
- 每轮记录选定和实际检索范围，后续范围调整不改写已有内容；无有效范围要求重新选择，部分可用明确标注遗漏库及原因，全部不可用终止，不自动扩围。
- 取消、实例删除、旧检索被替代后，迟到响应不得更新当前结果。以实例与请求身份识别结果归属，而不是把所有响应写入当前打开窗口。
- 问答历史完整保留，本轮模型上下文仅使用预算内近期完整轮次，不自动摘要；历史不能替代本轮证据。指代不明要求补充，不猜测。
- 每次引用定位实际内容版本，保存引用时文件名、完整引用切片及位置；资料重命名或覆盖不回写历史。完整旧副本已清理时仅展示证据快照，不能打开最新正文假装原文。
- 检索只返回切片，不生成回答；不显示跨模型统一可信度。再次提交以最新请求为准，旧响应不能覆盖新结果，即使新请求失败也不恢复旧请求为有效结果。
- 检索实例持久保存名称、最近已提交查询和范围，不保存命中结果或证据快照；重启显示待重新检索，必须由用户显式触发并重新校验范围。

### 契约与安全

- 每个切片先明确所需操作、字段和约束，前后端分别确认相同不可变契约摘要后实现。初次定义也是契约变更，模拟响应同样须符合已确认契约。
- 对齐范围包括方法、参数、媒体类型、必填与可空、数组和数值边界、未知字段、安全、成功错误状态、请求标识、文件响应及 SSE 事件；标识与时间按契约编码，不依赖 JavaScript 隐式转换。
- 消费统一错误与脱敏说明，不展示供应商原始异常或内部文件绝对路径。失效或错误响应不能用静默默认数据伪装成功。
- 当前本机网页遵循回环绑定、Host/来源限制、HttpOnly Cookie 和防跨站令牌。前端按正式契约携带会话与保护信息，不以“仅本机”省略安全控制。
- 模型密钥仅作为明确配置输入交后端，查询只消费掩码与状态；保持、替换、清除分别构造，掩码不回传为密钥。日志、前端持久化、截图、报告与提交均不得包含真实密钥。
- 配置缺失不回退环境变量。模型连接测试由后端进行，不发送用户资料，注明可能调用收费服务；普通测试及持续集成不调用真实模型。
- 模型和 Qdrant 故障仅阻断依赖它们的操作；本地资料操作继续可用，不在启动时一律锁死应用。

### 配置与运行数据

- 生成与嵌入模型独立配置；嵌入身份、维度或度量变更的索引影响需明确，密钥替换不等于重建。端点变化不能由前端凭相同模型名认定兼容。
- 数据目录是后端运行数据位置，不是源码目录、安装目录或浏览器下载目录。浏览器不能直接执行文件系统迁移。
- 迁移通过配置操作执行，暂停写入并展示实际阶段；目标须为空或不存在的合法本地绝对路径，拒绝相同、互相包含、根目录、源码误删和链接扩散风险。
- 成功切换前保留原数据；配置已切换但旧目录清理失败时继续使用新目录并提示残留，不引导回删新数据。Qdrant 原生存储不随应用数据目录搬迁。
- 备份恢复展示一致性与完整性结果、明文凭据包含情况、Qdrant 快照不包含及可能重新嵌入的费用；恢复不完整不能显示全部恢复成功。

### 原型探索与采纳记录

以下记录说明设计来源和首轮交付边界，不限制上述正式前端需求。后续页面采用“紧凑高效”，其余方案仅为探索记录；历史待定的颜色、布局和是否扩展业务流程不再作为未决问题。

- 主方向为甲“知识工作台”，均衡组织资料管理、知识库、检索与问答。乙“问答优先”、丙“资料研究台”未采纳。
- Q13—19 确认三套浅色可点击原型，分别为紧凑高效、宽松简洁、阅读友好；共用首页、问答、相同样例和操作能力，通过信息密度、留白、字体层级与色彩进行比较。
- 首轮演示首页跳转、新建与切换问答、模拟阶段、校验后固定回答及引用抽屉，不连接真实后端或模型，不进行收费调用。数据集、知识库、独立检索、设置以及完整重命名、删除、取消、失败交互未在首轮实现，后续按本文落实。
- 通过本地浏览器演示页交付，首轮桌面优先适配 1280～1920 像素。原型样例与模拟状态明确标识，不以静态展示证明正式业务完成。
- 已定位并阅读本机 ui-ux-pro-max 技能，执行两次设计系统检索；返回的宣传页结构不适合业务工作界面，未采纳该结构。
- 已读取 Anthropic 官方仓库的 frontend-design 技能并核对与项目内技能一致，作为原型视觉约束。来源为 <https://raw.githubusercontent.com/anthropics/skills/main/skills/frontend-design/SKILL.md>。
- 后续访谈沿用 Qx 问题编号及 1、2、3 选项编号；已确认内容直接用于实施，不因本次合并重新访谈。

### 当前证据与实施前提

原型仅有首页、问答、模拟阶段、固定回答与引用抽屉。前次测试结果记录在原型验证记录中；本次文档整理不重新执行或扩展这些测试结论。接口设计与签认单独追溯；正式业务接口、后端、统一构建、实现自动契约报告与桌面封装均未验收。

具体数值限额、超时、队列容量、模型标识兼容性及效果阈值在对应任务测量与契约定义时落实，不从原型样例推导。未确认的窗口关闭与后台驻留策略、桌面框架及原生桥接协议不影响本次规格发布，但在相应实施前必须明确。

# 接口契约协作规范

## 唯一依据与当前状态

`openapi.yaml` 是接口、字段、数据类型及约束的唯一正式定义，采用 OpenAPI 3.1，使用合法 YAML 子集的 JSON 语法保存。业务含义来自已确认规格；描述、错误说明和示例文案使用简体中文，协议及标识符保留实际写法。当前已完成覆盖全项目的接口设计，批准状态与最终摘要见 [开发共识记录](reviews/baseline.md)，前后端各自签认原文由该记录链接。

设计工作由前后端自行协商技术选择并互审；只有业务含义不确定或需要改变已确认规则时才向用户核实。全部操作与结构已写入唯一契约，[前端需求映射](frontend-requirements.md)覆盖 24 票与实际操作标识，[技术决策](design-decisions.md)解释共同选择，不作为第二份接口定义。后续切片直接采用已双签基线；新增或调整仍须先变更、校验和双审，再实现。设计双签不代表业务实现或运行对齐率 100%。

## 定义必须覆盖的内容

每个操作具有唯一 `operationId`、路径、HTTP 方法、说明、请求与响应定义。完整列出路径/查询/头部/Cookie 参数、媒体类型、请求体、字段类型、必填和可空差异、枚举、格式、长度、数值及数组边界、默认值、只读/只写、未知字段处理、安全、成功及错误状态码、统一错误码和请求标识。标识与时间的编码固定后双方一致，不靠 JavaScript 隐式转换适配。

文件上传定义 multipart 字段、类型/资源校验及逐项结果；下载定义媒体类型、响应头和二进制内容，不暴露内部绝对路径。SSE 也须在同一契约定义事件名、事件标识、数据结构、终态与断线查询语义，可通过契约扩展表达，不能只写“事件为字符串”。会话初始化、防跨站令牌、Cookie、Host/来源保护和敏感配置三种更新动作均纳入契约。

| 操作族 | 必须覆盖的业务 |
| --- | --- |
| 本机会话与系统 | 会话初始化、请求保护、统一错误、繁忙及服务状态 |
| 数据集 | 列表、创建、详情、名称说明修改、删除影响及级联删除 |
| 文件 | 批量上传逐项结果、元数据、重命名、最新预览下载、删除影响与删除、内容版本及引用定位 |
| 知识库 | 创建配置、发布下线、可用性检查、删除影响及删除 |
| 关联 | 数据集来源、单文件来源、排除及取消排除、按文件来源及处理状态 |
| 索引 | 任务查询、进度、单项及全部失败重试、生效版本及切换关系 |
| 检索 | 管理单库测试、普通多库检索、实例新建修改删除、提交及取消、范围缺失和结果定位 |
| 问答 | 实例/会话、历史、范围、提交任务、状态/结果/取消/SSE、引用版本快照 |
| 模型设置 | 生成与嵌入分别配置、掩码读取、保持/替换/清除、连接测试 |
| 运行数据 | 数据目录变更任务及失败残留、备份恢复、并发与资源参数 |

每个切片定义其全部所需操作；最终整表映射已确认契约，不能通过删除未实现操作缩小分母。未来任务未纳入契约时在覆盖清单中列为未定义，不得宣称全项目 100%。无前端消费的系统操作也须契约测试并由前端代理审阅，不要求伪造无意义界面调用。

## 任何接口变更的双向确认

1. 提出变更：列出业务原因、影响操作、字段与约束差异、消费者、兼容/迁移影响、测试及受影响任务。初次定义也走本流程。
2. 指定一名契约写入者，起草并静态校验；前端审查消费能力、交互和请求构造，后端审查验证、数据及安全，两方分别确认完全相同文件字节的 SHA-256。
3. 将确认记录写入 `reviews/<变更标识>.md`：变更内容、契约版本与摘要、操作范围、前端代理身份/结论/证据、后端代理身份/结论/证据。任何一方拒绝或尚未确认，不得把草案作为实现基线。
4. 送审前完成契约版本、样例及所有字节变更；两方确认后原样采纳该不可变契约，确认状态及覆盖清单保存在契约外，再进行实现。任何字段、类型、约束、事件、状态码或安全变动都须重新确认，包含兼容性增加，不允许单方修改后要求对方迁就。

正式契约只保存双方已确认的操作；草案差异留变更记录，不将“待确认接口”混进正式实现分母。后续编辑导致摘要改变，两方旧确认失效。全项目契约扩充需重新跑现有操作的回归，避免共享结构变更破坏已完成切片。

## 自动校验与报告

首个实现切片必须建立自动检查与报告生成器，并接入根 `mvn verify` 和持续集成。接口开发完成或契约变化后自动执行，不以手写报告代替：

1. 静态校验 OpenAPI、引用、唯一操作标识、安全及事件定义；骨架状态、空操作、未批准变更直接失败。
2. 建立“契约操作及约束 → 服务端路由/验证/序列化 → 客户端请求/响应消费 → 测试证据”映射，检查遗漏及未声明的公开业务接口。每条约束生成可追溯标识，分母来自契约和需求操作清单，不来自已有测试数量。
3. 提供方用真实应用接口和序列化结果校验成功、非法输入、错误和事件；消费方记录实际请求并验证响应消费及状态展示。约束涉及服务端行为时有真实行为测试，仅 lint、生成代码或校验样例不足以通过。
4. 对边界、必填/可空、枚举、未知字段、鉴权、上传/下载、任务状态和事件分别运行正反样例；测试无效输入应断言正确拒绝和无非法副作用。外部模型使用固定替身。
5. 自动输出机器 JSON 和中文 Markdown 到 `.scratch/technical-design/contract-reports/<运行标识>/`，即使失败也输出报告并返回非零退出码。生成产物不包含真实密钥、资料正文或个人数据。失败报告也需由持续集成保存供审阅。

报告须包含：契约版本/SHA-256、代码提交或工作区文件清单摘要（Git 未初始化也可追溯）、工具与环境、执行时间、原始结果位置、任务操作范围、全项目覆盖情况；逐操作与逐约束列出已实现、未实现、失败、未验证及具体差异，列明前端、后端和集成证据。

对齐率按“双方实现且所需检查通过的契约项数 / 该范围全部契约项数”计算，路径覆盖与字段/约束覆盖分别展示。分母为零、只有单方证据、跳过、未验证、范围外未实现均不得显示全项目 100%；切片报告可给出切片 100%，但必须同时展示全项目未完成范围。代码覆盖率 80% 不降低接口 100% 标准，生成报告也不等同于双方确认。

## 双方确认与完成门槛

采用两阶段门禁：根 `mvn verify` 校验已获双向批准的契约并生成不可变机器证据报告，不要求尚未生成的本次报告提前获得验收双签。随后两方签认该次报告；最终协调验收独立检查签认与摘要，不重新生成报告以验证签认。持续集成先保存不可变产物，再由验收阶段检查双签；缺验收签认时不能交付完成，但不让报告生成步骤形成循环。

两方分别审阅同一份自动报告，在 `reviews/<运行标识>-验收.md` 记录契约摘要、实现快照、报告 SHA-256、自身角色和结论及差异。自动生成器不能自动填“双方同意”，总协调不能代签。共同确认记录与机器报告分开，报告本体不靠手工改写为成功。

范围内全部操作/约束 100%、无差异无未验证项、前后端独立确认齐全、端到端通过，才可验收本切片。最终验收还要求操作清单全部完成且全正式契约 100%。实现或契约变化使相关报告与确认失效，必须重跑重审。

设计静态校验与结果见开发共识记录；它只核对契约。01 已接通根 `mvn verify`、提供方/消费方测试和实现自动报告，证据见 `.scratch/technical-design/implementation-01.md`；后续工程切片逐票扩展业务与验证范围，当前工作区须重新验证。

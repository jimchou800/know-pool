# 本地任务跟踪

## 文件与状态

每项功能在 `.scratch/<功能标识>/` 保留 `spec.md`；实现任务放 `issues/<两位编号>-<任务标识>.md`，索引为 `tickets.md`。原技术任务记录端到端状态，前端工作包只细化职责，不另建排期或代替整体完成。

文件顶部 `Status:` 仅用于分流：

| 状态 | 含义 |
| --- | --- |
| `needs-triage` | 等待维护者评估 |
| `needs-info` | 缺少必要信息 |
| `ready-for-agent` | 规格完整，可交给代理 |
| `ready-for-human` | 需要人工实施 |
| `wontfix` | 不予处理 |

正文“执行状态”使用未开始、进行中、已实现待统一验证、待验收、已完成或受阻，并记录双方负责人、共享写入者及证据。`ready-for-agent` 不表示实现完成。

## 批准、领取与完成

新拆分先保存草案，确认粒度和硬依赖后再发布独立任务。批准后将审批记录归入索引，正式范围以任务正文为准；不持续维护草案和正式票两份内容，不自动发布远程议题。讨论与已确认裁定追加在对应任务，业务规则仍归唯一规格。

领取按已批准依赖和编号推进，前置实现已提交并集成即可继续后续编码，不等待逐票验收。两领域按[协作流程](collaboration.md)共同推进，任务齐备后及时集成并标记待统一验证。

完成依靠[工程规范](engineering.md)的批次验证及[接口规范](api/README.md)的双方独立验收，不能以任一领域自检或历史快照通过替代。当前任务与工程状态统一由根 README 和任务索引导航，临时待办不另维护进度。

## 探索任务

探索使用 `map.md` 导航、`spec.md` 保存已确认规则；一项问题一个 `issues/` 文件，`Type:` 为 `research`、`prototype`、`grilling` 或 `task`。仅探索流程用 `claimed`、`resolved` 标识领取和解决，依赖由 `Blocked by:` 记录；不要将这两种状态用于普通实现任务。已归入规格的访谈细节不再在地图完整重复。

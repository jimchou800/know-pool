# 本地任务跟踪

## 文件组织

- 每个功能使用 `.scratch/<功能标识>/`。
- 需求规格保存为 `spec.md`。
- 每个实现任务单独保存为 `issues/<两位编号>-<任务标识>.md`，从 `01` 开始。
- 文件顶部使用 `Status:` 记录状态，取值见 `triage-labels.md`。
- 讨论记录追加到文件末尾的“讨论记录”章节。

## 技能操作

### 实现任务的批准、领取与完成

任务拆分先记录在 `.scratch/<功能标识>/tickets-draft.md`，列明端到端交付及真实阻塞关系。用户确认粒度、阻塞与合并拆分后，才按依赖顺序在 `issues/` 发布一票一文件；草案不是已经批准或可领取的任务。本项目使用本地跟踪，不自动发布远程议题。

普通任务保留五种分流状态，不用探索专用的 `claimed`、`resolved` 表示实现进度。任务以 `Status: ready-for-agent` 发布；另记录“执行状态：未开始、进行中、待验收、已完成、受阻”，前端负责人、后端负责人、共享文件写入者与验收证据。领取时先持久化负责人和执行状态，总协调避免重复领取。

前置任务仅当执行状态为已完成且证据已验收时解除阻塞，不能把分流值 `ready-for-agent` 当作已完成。实施工作遵循 `collaboration.md`，前后端工作包属于同一垂直切片，全部接口及约束按唯一契约 100% 对齐并经双方确认；代码、自动契约报告、交叉确认和端到端验收齐备才标记已完成。工具阻断或未测试项保留未完成状态。

“发布任务”表示创建对应的本地文件；“获取任务”表示读取指定文件。编号不唯一时，先确定所属功能。

## 探索任务

- 探索地图保存为 `.scratch/<探索标识>/map.md`，包含笔记、已定决策和待解问题。
- 子任务保存为 `issues/<两位编号>-<任务标识>.md`。
- `Type:` 使用 `research`、`prototype`、`grilling` 或 `task`。
- `Blocked by:` 列出前置任务编号；全部为 `resolved` 后才能开始。
- 优先选择编号最小、尚未解决、未被领取且无阻塞的任务。
- 开始前将 `Status:` 设为 `claimed` 并保存。
- 完成后追加“解答”章节，将状态改为 `resolved`，并在地图中补充结论及链接。

探索中的 `claimed`、`resolved` 仅用于探索任务的执行状态；普通任务使用五种分流状态。
